# Migrating to 0.2.0

Version 0.2.0 changes three behaviours introduced or clarified by pull request
[#208](https://github.com/leynos/post-turn-quality-stop-hook/pull/208), and
adds a consecutive-failure breaker from pull request
[#227](https://github.com/leynos/post-turn-quality-stop-hook/pull/227). Review
these changes before upgrading an existing installation.

## `gate_quality_checks = false` now disables the quality gate

Earlier releases parsed `gate_quality_checks` but did not act on a `false`
value. The hook now honours it: the quality gate is disabled, and the hook
skips build-driver selection, target enumeration, and target execution. It
continues directly to the branch-state gates.

An existing configuration that sets `gate_quality_checks = false` will
therefore stop running build targets. To keep the previous behaviour, set the
effective value to `true`, or remove the setting from every configuration the
hook loads, including the XDG configuration file. Removing only a
repository-local setting leaves an inherited XDG value in force.

## Captured build output is plain

The hook removes `FORCE_COLOR` and `CLICOLOR_FORCE` from the environment it
passes to build commands, and sets `NO_COLOR=1`. A build tool can no longer
force colour into the output the hook captures. Coloured build output is
therefore unavailable through the hook; run the build command directly in a
terminal when you need it.

## Escape sequences are removed before truncation

Captured output has ANSI escape sequences removed before the
`POST_TURN_MAX_OUTPUT_CHARS` limit applies. Colour codes, cursor movement,
terminal titles, and hyperlinks cannot corrupt the blocking report or consume
its output budget.

No action is required for this change unless a repository relied on escape
bytes appearing in captured output, which was never a supported contract.

## Consecutive blocking decisions now short-circuit the hook

The hook now counts consecutive blocking decisions per working directory. After
`max_consecutive_failures` consecutive blocks (default `10`) in the same
directory, the next stop runs no checks. It prints a non-blocking
`systemMessage` instead, resets the count, and checks again on the following
stop.

Configuration errors and invalid CLI arguments are blocks too, so they also
count. An agent that cannot clear a block is therefore released after the limit
rather than looping indefinitely.

To keep the previous behaviour, where the hook blocks on every failing stop, set
`max_consecutive_failures = 0` in the effective configuration. See
[Repeated failures](../users-guide.md#repeated-failures) for how the count is
stored and reset.
